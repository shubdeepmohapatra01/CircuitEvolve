1. The idea: mutator → verifier → metric, inside a simple selection loop¶

The LLM is only a mutation operator: it sees one small window of the circuit and proposes a replacement. An exact/numerical verifier that the search cannot modify decides whether the replacement is admissible, and a metric with BQSKit's error convention decides whether it is better. A playbook of LLM-written hints evolves between calls, but it can only change proposals, never acceptance.

Part Module (circuitevolve/) Role
circuit + windows core/circuit.py TKET input, QASM I/O, windows ≤ 4 qubits / ≤ 40 ops (BQSKit QuickPartitioner), splice
mutator core/mutator.py (+ core/refit.py) prompt for one window; parses ```window (exact rewrite) and ```fix (fix-and-refit) blocks with regexes, never eval
verifier core/verifier.py → frozen blocks/verify_block.py exact D[ω] check for Clifford+T windows, else operator distance ≤ allowance; whole circuit vs the original
metric core/metric.py T-count: remaining Rz via gridsynth at ε_rz = ε_synth / N_Rz, π/4 multiples exact
error ledger core/ledger.py splits ε between window rewrites (measured distances) and final synthesis; bound ≤ ε
selection core/loop.py archive (best + 3), windows by T-cost, accept on measured improvement, one log line per LLM call
playbook search/playbook.py reflector-written rules, A/B-gated: promoted only on measured T reductions

5. The playbook learned in stage 1¶

A reflector call (every 10 proposer calls) reads recent verifier outcomes and proposes short rules. Each rule is A/B-tested: shown in some prompts and hidden in others; it is promoted to active only if prompts that showed it led to more accepted, T-reducing proposals, and retired if not. The playbook started empty and was carried across the stage-1 runs in a fixed order. Below: the active rules with their evidence, and the status counts after each run.

6. Does the shared playbook help? (train / freeze / test)¶

The stage-1 playbook in section 5 was learned and used on the same circuits, so it cannot show that its rules transfer. This experiment separates learning from testing: a fresh, empty playbook is learned on development circuits only (smaller members of the qft / qpe / qae families), then frozen and hashed, then tested on held-out circuits in three arms: no playbook, the frozen learned playbook, and a placebo playbook holding one hand-written generic rule of similar length that is rendered into the prompt by the same code path. Every arm gets the same number of proposer calls per run and no reflector calls, so the playbook block is the only difference in the prompt. The design parameters below are read from the run files in results/window_runs/ablation_v1/.
